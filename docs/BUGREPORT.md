## 3. Подтверждённые дефекты

### XW-01. `servers edit` удаляет или перезаписывает профили

**Важность:** критическая — потеря данных.  
**Где:** `cli/servers.go:200-206`, `backend/store.go:85-97`, `backend/store.go:137-144`.

Логика переименования сначала сохраняет профиль под новым именем, затем удаляет старый:

```go
if err := st.SaveProfile(newName, *np); err != nil { ... }
if newName != name {
    _ = st.DeleteProfile(name)
}
```

Проверки, что новое имя после `sanitizeProfileName` указывает на тот же файл, нет. Проверки существования целевого профиля тоже нет.

#### Сценарий 1: «переименование» в имя, которое санитизируется в тот же файл

```powershell
& $X servers add 'wdtt://1.1.1.1:1:2:3:pass#CollA'
& $X servers edit 'CollA 1' -name 'CollA? 1'
```

Наблюдаемый результат:

```text
Профиль сохранён: CollA 1
Сохранено и переименовано: CollA 1 → CollA? 1
--- файлы ---
--- список ---
Серверов нет. Добавьте: xwdtt servers add "wdtt://..."
```

`CollA? 1` санитизируется в `CollA 1`, `SaveProfile` пишет тот же файл, после чего `DeleteProfile("CollA 1")` удаляет его. Команда сообщает об успехе, профиль исчез.

#### Сценарий 2: смена только регистра на Windows

```powershell
& $X servers add 'wdtt://1.1.1.1:1:2:3:pass#Case'
& $X servers edit 'Case 1' -name 'case 1'
```

Результат:

```text
Сохранено и переименовано: Case 1 → case 1
Серверов нет.
```

На регистронезависимой ФС `Case 1.json` и `case 1.json` — один файл. После сохранения исходное имя удаляется.

#### Сценарий 3: переименование поверх существующего профиля

```powershell
& $X servers add 'wdtt://1.1.1.1:1:2:3:passA#CollA'
& $X servers add 'wdtt://2.2.2.2:2:2:2:passB#CollB'
& $X servers edit 'CollA 1' -name 'CollB 1'
```

Результат:

```text
Сохранено и переименовано: CollA 1 → CollB 1
CollB 1.json
Имя:      CollB 1
Адрес:    1.1.1.1:1
Пароль:   passA
```

Профиль `CollB 1` перезаписан данными `CollA 1`, исходный `CollA 1` удалён. Пользователь не получает ни предупреждения, ни подтверждения.

**Последствия:** потеря профилей, потеря `DeviceID`, подмена сервера. Особенно опасно, потому что команда возвращает код 0 и пишет «Сохранено».

**Что исправить:**

- запрещать `newName`, если `sanitizeProfileName(newName) == sanitizeProfileName(name)`;
- сравнивать пути с учётом регистронезависимости Windows;
- отказывать при существующем целевом профиле без явного `--force`;
- удалять старый профиль только после успешной записи и только если это физически другой файл;
- проверять ошибку `DeleteProfile`.

### XW-02. `servers add` молча перезаписывает профиль

**Важность:** критическая — потеря данных.  
**Где:** `cli/link.go:111-145`, `backend/store.go:118-135`.

`autoName` проверяет свободность имени по ключам `ListProfiles`, то есть по уже санитизированным именам файлов, но сравнивает их с **сырым** именем из ссылки. `SaveProfile` затем санитизирует имя ещё раз. В результате разные ссылки могут попасть в один файл.

#### Регистр

```powershell
& $X servers add 'wdtt://1.1.1.1:1:2:3:passA#Case'
& $X servers add 'wdtt://2.2.2.2:2:2:2:passB#case'
```

Наблюдаемый результат:

```text
Профиль сохранён: Case 1
Профиль сохранён: case 1
```

В каталоге остаётся один файл `case 1.json`; в нём уже второй peer (`2.2.2.2:2`, `passB`). Первый профиль потерян. `SaveProfile` при этом может подхватить `DeviceID` старого профиля, что делает перезапись ещё менее заметной.

#### Санитизационные коллизии

```powershell
& $X servers add 'wdtt://1.1.1.1:1:2:3:passA#!!!'
& $X servers add 'qwdtt://config?name=%23%23%23&peer=2.2.2.2:2&pass=passB'
```

Результат:

```text
Профиль сохранён: !!! 1
Профиль сохранён: ### 1
```

Оба имени после санитизации дают `1`, остаётся один `1.json` со вторым профилем. При этом пользователю показывается исходное, несанитизированное имя.

**Что исправить:** санитизировать имя до проверки коллизий; проверять существование целевого файла; возвращать ошибку и требовать явного подтверждения перезаписи.

### XW-03. `servers add` сообщает об успехе при ошибке сохранения

**Важность:** высокая — ложное состояние, потеря введённых данных.  
**Где:** `cli/link.go:131`, `cli/link.go:137-144`, `cli/servers.go:86-92`.

Оба вызова `SaveProfile` в `upsertFromLink` игнорируют ошибку:

```go
_ = st.SaveProfile(name, p)
```

`serversAdd` всегда печатает «Профиль сохранён» / «Профиль обновлён» и возвращает 0.

Воспроизведение: создаём каталог с именем будущего файла, чтобы `os.Rename` не смог заменить его файлом.

```powershell
New-Item -ItemType Directory -Path "$env:APPDATA\xwdtt\servers\Broken 1.json" -Force | Out-Null
& $X servers add 'wdtt://1.1.1.1:1:2:3:pass#Broken'
```

Результат:

```text
Профиль сохранён: Broken 1
exit=0
--- entries ---
d----- Broken 1.json
-a---- Broken 1.json.tmp
Серверов нет. Добавьте: xwdtt servers add "wdtt://..."
```

Профиля нет, но пользователь видит успех. Остаётся `.tmp` с данными (включая пароль). То же поведение возможно при нехватке места, запрете записи и т.п.

**Что исправить:** проверять ошибку `SaveProfile`, не печатать успех при ошибке, возвращать код 1 и очищать `.tmp`.

### XW-04. Паника интерактивного режима на строке из кавычек

**Важность:** высокая — аварийное завершение, код 2.  
**Где:** `cli/interactive.go:43-44`, `cli/interactive.go:56`, `cli/interactive.go:135-158`.

`SplitCommandLine` не добавляет пустой аргумент, если строка состоит только из `"`. `dispatchInteractive` без проверки обращается к `args[0]`.

Воспроизведение:

```powershell
'""' | & $X
```

Результат:

```text
XWDTT 1.6.0 — интерактивный режим. Команда help — справка, quit — выход.
xwdtt> panic: runtime error: index out of range [0] with length 0

goroutine 1 [running]:

    F:/etc/PWDTT/cli/interactive.go:56 +0x652
xwdtt/cli.runInteractive()
    F:/etc/PWDTT/cli/interactive.go:44 +0x20c
...
exit=2
```

Достаточно любой строки, которая после разбора даёт пустой срез: `""`, `"`, `"""` и т.п.

**Что исправить:** в `dispatchInteractive` добавить `if len(args) == 0 { return false }`; в `SplitCommandLine` корректно обрабатывать незакрытую кавычку.

### XW-05. `servers show CON` / `AUX` зависает

**Важность:** высокая — CLI-команда не завершается, процесс приходится убивать.  
**Где:** `backend/store.go:85-115` (нет проверки зарезервированных имён Windows).

`sanitizeProfileName` разрешает `CON`, `PRN`, `AUX`, `NUL`, `COM1`…`LPT9`. При обращении к `servers\CON.json` Windows воспринимает `CON` как устройство, и `os.ReadFile` блокируется.

Безопасное воспроизведение с таймаутом:

```powershell
$p = Start-Process $X -ArgumentList 'servers','show','CON' -PassThru
if (-not $p.WaitForExit(3000)) {
    "TIMEOUT"
    Stop-Process -Id $p.Id -Force
}
```

Наблюдалось: процесс не завершается за 3 секунды, убит принудительно. `servers show NUL` возвращает «не найден», `AUX` также зависает. `servers list` такие имена не показывает.

**Что исправить:** запрещать зарезервированные имена Windows (включая варианты с расширением и хвостовыми точками/пробелами) на уровне `sanitizeProfileName`/`SaveProfile`/`LoadProfile`.

### XW-06. Нет валидации `-workers`

**Важность:** средняя — некорректные данные профиля, скрытое поведение.  
**Где:** `cli/servers.go:222`, `cli/servers.go:249`; ограничение только в `core/main.go:252-260`.

`servers edit -workers` принимает любое `int`:

```powershell
& $X servers edit 'W 1' -workers -5
& $X servers edit 'W 1' -workers 2147483647
```

Результат:

```text
Сохранено: W 1
edit_neg_exit=0
Сохранено: W 1
edit_max_exit=0
ИМЯ  АДРЕС      ХЕШИ  TCP  ВОРКЕРЫ
W 1  1.1.1.1:1  0     нет  2147483647
```

Отрицательное значение сохраняется, но `servers list` показывает `-`, потому что выводит только `> 0`. При подключении ядро всё равно приводит число к 108 (или к 24 для `<= 0`), то есть профиль хранит одно, а работает другое. Это затрудняет диагностику.

**Что исправить:** валидировать диапазон (`0` = авто, либо `1..108`), отклонять отрицательные и слишком большие значения на уровне CLI и/или `SaveProfile`.

### XW-07. BOM в `config.json` тихо сбрасывает настройки

**Важность:** высокая — пользователь теряет настройки, следующая запись закрепляет дефолты.  
**Где:** `backend/store.go:47-56`.

`json.Unmarshal` не принимает UTF-8 BOM. Вместо ошибки `LoadSettings` молча возвращает дефолты: `AutoStart=true`, `routeMode=full`, `workers=auto`, `obfs=audio`.

Воспроизведение:

```powershell
$bom = New-Object Text.UTF8Encoding($true)
[IO.File]::WriteAllText("$env:APPDATA\xwdtt\config.json",
  '{"autoStart":false,"routeMode":"split","workers":3}', $bom)
& $X settings get
& $X settings set workers 9
[IO.File]::ReadAllText("$env:APPDATA\xwdtt\config.json")
```

Наблюдаемый результат:

```text
autostart      on
doh            yandex
obfs           audio
obfs-accepted  off
turn-tcp       off
workers        auto
...
{
  "autoStart": true,
  "obfsMode": "audio",
  "obfsAccepted": false,
  "turnTcp": false,
  "workers": 9,
  "doh": "yandex",
  "routeMode": "full",
  "splitRoutes": null
}
```

Исходные `autoStart:false` и `routeMode:"split"` потеряны. Пользователь не видит предупреждения.

**Что исправить:** срезать BOM перед `Unmarshal`; при ошибке парсинга не применять дефолты молча, а логировать/показывать предупреждение и не перезаписывать исходный файл без подтверждения.

### XW-08. `xwdtt update` всегда падает с 404

**Важность:** высокая — функция обновления не работает.  
**Где:** `backend/update.go:26`, `backend/update.go:36-38`.

```powershell
& $X update
```

Результат:

```text
Не удалось проверить обновления: github api status: 404
exit=1
```

Проверка API на момент отчёта:

```text
GET https://api.github.com/repos/zxcursedzxc0721/XWDTT          -> 200
GET https://api.github.com/repos/zxcursedzxc0721/XWDTT/releases  -> 200, []
GET https://api.github.com/repos/zxcursedzxc0721/XWDTT/releases/latest -> 404
```

У проверенного бинарника зашит старый репозиторий (`luminescq/PWDTT`), который также отдаёт 404. Но и HEAD-код с новым репозиторием не работает: GitHub возвращает 404 для `/releases/latest`, когда релизов нет. Код считает любой не-200 фатальной ошибкой.

**Что исправить:** трактовать 404 и пустой список релизов как «обновлений нет»; различать «нет релизов» и «ошибка API»; показывать понятное сообщение.

### XW-09. `parseVersion` не различает pre-release

**Важность:** средняя — пользователи pre-release не получают финальный релиз.  
**Где:** `backend/update.go:110-132`.

```go
func parseVersion(v string) [3]int {
    v = strings.TrimPrefix(v, "v")
    parts := strings.SplitN(v, ".", 3)
    for i, p := range parts {
        fmt.Sscanf(p, "%d", &result[i])
    }
    return result
}
```

`1.6.1-beta` и `1.6.1` дают `[1,6,1]`. `isNewer` возвращает `false`, поэтому финальный `1.6.1` не предлагается пользователю `1.6.1-beta`. Аналогично `1.6.1-rc1`.

**Что исправить:** реализовать сравнение semver с pre-release-частью (например, `golang.org/x/mod/semver`), либо явно считать pre-release младше финала.

### XW-10. Принимаются невалидные peer-адреса

**Важность:** средняя — создаётся нерабочий профиль.  
**Где:** `cli/link.go:97`, `cli/link.go:64-66` — проверяется только непустота.

```powershell
& $X servers add 'wdtt://a:b:2:3:p#Bad'
& $X servers add 'wdtt://x:2:2:3:p#Bad2'
```

Результат:

```text
Профиль сохранён: Bad 1
add_exit=0
Профиль сохранён: Bad2 1
add2_exit=0
ИМЯ     АДРЕС  ХЕШИ  TCP  ВОРКЕРЫ
```

**Что исправить:** валидировать `net.SplitHostPort`, порт `1..65535`, IP или допустимое DNS-имя; проверять порты в ссылке.

### XW-11. После ошибки записи остаётся `.tmp` с настройками

### XW-14. `patchMTU` дублирует MTU при `MTU=...` без пробелов

**Важность:** низкая — дублирование ключа, потенциальная хрупкость.

## 4. Дефекты, подтверждённые только статическим анализом

Эти пункты не воспроизводились на живой сети и не меняли маршруты на машине. Они перечислены как высокорисковые места, требующие тестирования в изолированной ВМ.

### XW-16. Жёсткое восстановление метрики шлюза `35` и потеря `9999` после краша

**Важность:** высокая.  
**Где:** `backend/wg.go:343-355`, `backend/wg.go:387-396`.

В full-режиме приложение поднимает метрику физического default-маршрута до `9999`, чтобы туннель выиграл:

```go
_ = runCmdWindows("route", "change", "0.0.0.0", "mask", "0.0.0.0", gw, "metric", "9999")
```

При teardown метрика восстанавливается не сохранённым значением, а константой:

```go
_ = runCmdWindows("route", "change", "0.0.0.0", "mask", "0.0.0.0", w.physGW, "metric", "35")
```

Проблемы:

1. Если исходная метрика была не `35` (например, `25`, `50`, `70`), после отключения приоритет маршрутов меняется.
2. Если приложение/питание упало между `metric 9999` и teardown, default-маршрут остаётся с метрикой `9999`. На следующем старте Windows-очистки нет: `CleanupStaleExcludeRoutes` для Windows — no-op. Машина может остаться без нормального выхода в сеть.
3. Ошибки `route change` игнорируются, поэтому даже штатный teardown может не восстановить маршрут.
4. Если за время сессии сменился шлюз (DHCP, Wi-Fi), восстановление идёт по старому `physGW`.

На тестовой машине `route print 0.0.0.0` показывает суммарную метрику `70` при компоненте `35`. Совпадение с константой здесь случайно и не гарантирует корректность на других системах.

**Что исправить:** сохранять исходную метрику (и, возможно, весь маршрут) до изменения; восстанавливать точное значение; при старте обнаруживать и чинить «зависший» `9999`; не игнорировать ошибки `route change`; при смене шлюза не трогать новый маршрут.

### XW-17. Full-режим продолжает работу при неудачном определении шлюза

**Важность:** высокая.  
**Где:** `backend/wg.go:343-370`, `backend/wg.go:508-521`.

`defaultGatewayWindows` запускает `cmd /c route print 0.0.0.0` и берёт первое совпадение `0.0.0.0 0.0.0.0`, поле `[2]`. При ошибке команды, неожиданном формате или отсутствии default-маршрута возвращается пустая строка. В `applyWindows` это не фатально:

```go
gw := defaultGatewayWindows()
if plan.HijackDefault {
    ...
    if gw != "" {
        w.physGW = gw
        _ = runCmdWindows("route", "change", ..., "metric", "9999")
    }
}
...
if gw != "" {
    excludes = plan.ExcludeRoutes
    ...
}
```

Если `gw == ""`:

- default-маршрут не перехватывается;
- exclude-маршруты (TURN/VK/DNS) не добавляются;
- туннельные маршруты всё равно добавляются;
- приложение сообщает «Туннель поднят».

В full-режиме это может привести к утечке трафика мимо туннеля, петле TURN или нерабочему подключению. Ошибка только логируется строкой `Default gateway: ` (пусто), но подключение не прерывается.

**Что исправить:** считать пустой шлюз фатальной ошибкой для full-режима; либо явно переходить в безопасный split-режим с предупреждением; проверять, что `route change` действительно применился.

### XW-18. На Windows не чистятся «зависшие» exclude-маршруты

**Важность:** средняя.  
**Где:** `backend/wg.go:71-81`, `backend/wg.go:358-371`, `backend/wg.go:398-405`.

`CleanupStaleExcludeRoutes` вызывает очистку только на Darwin:

```go
if runtime.GOOS == "darwin" {
    cleanupStaleExcludeRoutesDarwin(logf)
}
```

На Windows exclude-маршруты добавляются через `route add` и удаляются только если `w.activeExcludeRoutes` заполнен в текущем процессе. После краша/`taskkill` это состояние теряется, маршруты остаются. Они могут навсегда уводить TURN/VK/DNS мимо туннеля и мешать следующему подключению.

**Что исправить:** реализовать Windows-очистку по известному набору CIDR при старте; либо маркировать маршруты и удалять их по метрике/интерфейсу; вести журнал добавленных маршрутов.

### XW-19. Ошибки пакетного удаления маршрутов игнорируются

**Важность:** средняя.  
**Где:** `backend/routes_apply.go:62-75`, `backend/routes_apply.go:32-58`.

Для `<= 32` маршрутов:

```go
for _, cidr := range cidrs {
    _ = runCmdWindows("netsh", "interface", "ip", "delete", "route", cidr, iface)
}
```

Для `> 32`:

```go
if warnings, err := runNetshRouteScript("delete", cidrs, iface); err == nil && warnings != "" {
    log.Printf(...)
}
```

Если `netsh -f` вернул ошибку, она не логируется вообще. Если ошибка была в отдельных строках, но процесс завершился с кодом 0, логируются только warnings. В результате после отключения могут остаться маршруты, а пользователь не узнает причину.

Дополнительно `applyTunnelRoutes` при ошибке пакетного добавления возвращает весь список `cidrs` как «активные», хотя часть маршрутов не добавилась.

**Что исправить:** проверять и логировать `err` всегда; сверять фактическое состояние `route print`; возвращать только реально добавленные маршруты; повторять/откатывать при ошибке.

### XW-20. Нет блокировки единственного экземпляра

**Важность:** средняя.  
**Где:** `main.go:10-12`, `backend/bridge.go:17`, `backend/wg.go:34-51`.

Мьютекс `Bridge.mu` защищает состояние только внутри одного процесса. Блокировки named mutex / lock-файла на уровне приложения нет. Два экземпляра `xwdtt.exe` могут одновременно:

- создавать/закрывать один и тот же `xwdtt-wg` адаптер;
- менять метрику default-маршрута;
- удалять маршруты друг друга;
- писать в одни и те же профили/логи.

Второй экземпляр при teardown может снять туннель первого или удалить его маршруты.

**Что исправить:** named mutex (`CreateMutex`/`LockFileEx`) на время работы; второй экземпляр должен завершаться с понятным сообщением. Для CLI-команд, меняющих состояние, — отдельная блокировка.

### XW-21. `wintun.dll` не проверяется и загружается в привилегированном процессе

**Важность:** высокая (при локальном доступе к каталогу с exe).  
**Где:** `backend/wg.go:424-437`.

```go
dst := filepath.Join(filepath.Dir(exe), "wintun.dll")
if _, err := os.Stat(dst); err == nil {
    return nil
}
return os.WriteFile(dst, wintunDLLData, 0644)
```

Если `wintun.dll` уже существует, приложение доверяет ему без проверки хэша/подписи/версии. `tun.CreateTUN` загружает DLL из окружения процесса. Интерактивный режим запускается с повышением прав (UAC), поэтому подмена DLL в каталоге, доступном на запись непривилегированному пользователю (типичный portable-запуск из `Downloads`/`%TEMP%`), даёт выполнение кода в elevated-контексте.

Даже если каталог защищён (Program Files), это нарушает целостность: старая/несовместимая DLL может привести к падению или неверной работе TUN.

**Что исправить:** сверять SHA-256 существующего файла со встроенным; при несовпадении перезаписывать или отказываться; по возможности загружать DLL из защищённого каталога с проверенной подписью; не доверять файлу рядом с exe.

### XW-22. Replay-window не сбрасывается при смене SSRC

**Важность:** средняя.  
**Где:** `core/obfs.go:31-61`.

Комментарий обещает начать заново при смене SSRC:

```go
} else if w.ssrc != ssrc {
    // смена SSRC (переподключение к тому же relay) - начинаем заново.
    return false
}
```

Но `return false` означает «пакет отклонён», а не «сбросить окно». После смены SSRC (перезапуск peer/relay, повторное подключение) `w.ssrc` остаётся старым, и **все** последующие пакеты отклоняются до перезапуска процесса.

**Что исправить:** при смене SSRC очищать `seen`, обновлять `ssrc`, `highestTime`, `initialized` и принимать пакет; либо явно документировать, что SSRC неизменен, и убирать ложный комментарий.

### XW-23. `ReadLatestLog` может выбрать не тот файл

**Важность:** низкая.  
**Где:** `backend/store.go:222-235`, `backend/store.go:187-197`.

```go
entries, err := os.ReadDir(dir)
latest := entries[len(entries)-1]
data, err := os.ReadFile(filepath.Join(dir, latest.Name()))
```

`os.ReadDir` сортирует по имени. Для файлов `YYYY-MM-DD_HH-MM-SS.log` это совпадает с хронологией, но:

- в каталоге могут быть посторонние файлы (`.tmp`, `desktop.ini`, вложенный каталог) — будет выбран последний по имени, а не лог;
- `OpenLogFile` использует `os.Create` с точностью до секунды; два запуска в одну секунду перезапишут один файл;
- нет фильтра по расширению `.log`.

**Что исправить:** фильтровать `.log`, парсить время из имени, выбирать максимум; использовать `O_EXCL`/микросекунды для имён логов.

### XW-24. Файлы с секретами создаются с режимом `0644`

**Важность:** низкая (для Windows — защита наследуемыми ACL; для Unix/переноса — значимо).  
**Где:** `backend/store.go:285-292`, `backend/wg.go:436`.

`atomicWrite` и `extractWintun` используют `0o644`. Профили содержат пароль, `config.json` — настройки, `.tmp` — их копию. На Unix это делает файлы читаемыми всем пользователям; на Windows режим в основном игнорируется, но при копировании каталога/переносе на Linux/macOS права сохранятся.

**Что исправить:** `0600` для файлов с секретами и `0700` для каталогов; на Windows явно выставлять ACL, если требуется защита от других локальных пользователей.

## 5. Что не является дефектом (проверено, чтобы не дублировать ложные находки)

- **`stats` и `logs` недоступны как отдельные CLI-команды.** Это соответствует документации: они работают только в интерактивном режиме. Не баг.

- **`servers list` не показывает битый профиль.** Само по себе скрытие — часть XW-13; отдельным дефектом считать не нужно.
- **`xwdtt update` с 404 — не проблема сети.** Репозиторий доступен; 404 приходит от GitHub из-за отсутствия релизов. Это XW-08.
